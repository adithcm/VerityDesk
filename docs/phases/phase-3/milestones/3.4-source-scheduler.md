# Milestone 3.4: Source Scheduler

Status: Complete

## Goal

Add a backend ingestion runner that can trigger RSS and official API ingestion on demand, enforce a simple overlap lock, and store daily schedule configuration for later automation.

## Included

- Ingestion runner service.
- `POST /api/v1/ingestion/run` endpoint.
- `GET /api/v1/ingestion/schedule` endpoint.
- `POST /api/v1/ingestion/schedule` endpoint.
- Run modes for `all`, `rss`, and `official_api`.
- Optional source-key filtering for targeted ingestion runs.
- In-process run lock to prevent overlapping ingestion jobs.
- Partial-success reporting when one source fails but others complete.
- Daily schedule configuration foundation.
- Tests for combined runs, source filtering, partial success, lock behavior, endpoint triggering, and schedule configuration.

## Manual API Run

Run all configured ingestion sources:

```http
POST /api/v1/ingestion/run
```

Example body:

```json
{
  "mode": "all",
  "source_keys": []
}
```

Run only RSS sources:

```json
{
  "mode": "rss",
  "source_keys": []
}
```

Run one source:

```json
{
  "mode": "official_api",
  "source_keys": ["fred-api"]
}
```

## Not Included Yet

- Always-on background scheduling.
- Durable scheduler state in the database.
- Frontend run button.
- Source health/freshness read APIs.
- Scheduler retry policy.

Those are covered by later Phase 3 milestones.

## Definition Of Done

- Backend can trigger ingestion through an API endpoint.
- Caller can choose all sources, RSS only, official APIs only, or specific source keys.
- Concurrent runs are rejected with an `already_running` response.
- Failures in one source can be reported without hiding successful source results.
- Backend tests and lint pass.
